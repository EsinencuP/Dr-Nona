## Moderation and boundaries

New rows default to `PENDING`. Only authenticated CRM administrators can submit decisions: thumbs up sets `APPROVED`; thumbs down sets `REJECTED`. Rejected rows remain in CRM history. Changing an earlier decision is supported and audited. Version checks reject concurrent stale decisions; mutation and audit share a transaction. Public reads select only approved rows with public fields, and suppress reviews of products no longer published/ready. Public responses are never cached, so a rejection removes the review on the next read.

Submissions validate name/text bounds, exact consent, supported locale and published SKU. A honeypot, existing persistent application rate guard, bounded JSON payload and HMAC proxy verification protect the endpoint. Review signatures are separated by purpose, method and query. Retries reuse an idempotency key; changed text receives a new key. A pending acknowledgement is returned only after persistence. Network/provider/database failure leaves the form text in place.

The user authorized review functionality, not fabricated testimonials or automatic approval of regulated claims. Administrators must reject personal data and unapproved medical/scientific claims before publication. Consent wording, data-controller identity and retention are **PENDING APPROVAL** under existing legal/privacy release blockers. The form explicitly requests permission to publish the display name and review after moderation; this does not resolve the production legal gate. No sample customer reviews ship with the feature.
